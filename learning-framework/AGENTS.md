# Learning Framework Agent Guide

本文件用于约束后续在 `learning-framework` 项目中工作的 Codex / 代码代理。

## 核心目标

- 本项目是为了学习 `claudecode-project` 的源码结构，不是做一个随意发挥的独立 demo。
- 新增代码、重构代码、命令设计、目录组织、命名方式，应尽量贴近 `claudecode-project` 的真实实现思路。
- 如果为了教学做简化，必须保留和源码的映射关系，并明确写出“源码怎么做、这里为什么简化、差异在哪里”。

## 代码实现要求

- 优先模仿 `claudecode-project` 的职责划分：
  - `main.tsx` 负责入口装配和命令路由。
  - `cli/handlers/` 负责交互式或特定命令分支的执行。
  - `cli/print.ts` 负责非交互式打印路径。
  - `services/` 负责组织业务数据，不负责随意读写磁盘。
  - `utils/sessionStorage.ts` 这类工具负责持久化、恢复、路径规则等底层逻辑。
- 不要为了“更简单”把本应拆分到不同层的逻辑重新揉回一个文件。
- 命名尽量贴近源码语义，避免创造和源码风格差距过大的新抽象名。
- 如果必须引入学习版专用名字，优先把它做成“学习别名”或“源码语义的简化包装”，不要让它成为主实现路径。

## 注释要求

- 所有新增的学习型注释，必须尽量包含下面三类信息：
  - `对应追源码位置`：明确写出 `claudecode-project` 里应去看的文件路径。
  - `源码如何实现 / 使用`：说明源码里这块逻辑是怎么被调用、怎么组织、怎么协作的。
  - `为什么这样设计`：说明职责边界、分层原因、演进价值。
- 不要只写“这个文件对应 Claude Code 某模块”这种过于宽泛的注释。
- 不要只解释概念，不指出源码落点。
- 不要只标源码位置，不解释实现方式和设计原因。

## 简化要求

- 可以简化功能规模，但尽量不要简化架构方向。
- 优先做“更小的 Claude Code”，而不是“更容易懂但结构完全不同的 demo”。
- 如果当前实现和 `claudecode-project` 差别较大，需要主动往源码结构收敛。

## 命令设计要求

- 交互式命令尽量贴近 Claude Code 的默认启动 / handler 分层方式。
- 非交互式命令尽量贴近 `cli/print.ts`、`resume`、`status`、`doctor` 这类源码路径的设计思路。
- `start`、`inspect` 这类学习命令如果保留，应视为学习别名，主实现路径应尽量贴近源码结构。

## 修改原则

- 修改前先看当前学习版实现和 `claudecode-project` 对应源码，再决定如何补充。
- 优先做“结构对齐”的修改，而不只是“功能可运行”的修改。
- 如果某个实现明显偏离源码，应优先修正结构，再继续加功能。
